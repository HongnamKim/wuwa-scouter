# 위키 원문에서 프로젝트 데이터 작성하기

작성 기준: 2026-09-14, 저장소 `f9e85d3`. 캐릭터 18명, 무기 49개, 화음 세트 16개, 자유 2세트 효과 3개를 조사했다. 최초 조사 시 버프는 캐릭터 222개, 무기 108개, 세트 40개, 메인 에코 30개였다. 같은 날 점검 오류 수정과 기록 전용 효과 보완 후 캐릭터 버프는 228개다.

이 문서는 위키 자료 → LLM 변환 초안 → 사람의 수정·검수 흐름을 위한 진입 문서다. 상세 버프 판정에는 [버프 기록 규칙 v2](buff-recording-rules-v2.md)를 함께 사용한다. [기존 규칙](buff-recording-rules.md)은 과거 판단을 추적하기 위해 유지한다. v2는 현재 데이터와 원문을 대조한 개정안이다. 이후 사용자 요청으로 반영한 데이터·계산 수정과 남은 한계는 v2 §11에 기록했다.

## 1. 근거를 구분한다

| 구분 | 무엇을 확인하는가 | 근거 |
|---|---|---|
| 원문 사실 | 수치, 대상, 조건, 피해 판정, 공명 체인 | 지정한 게임 버전의 스킬 상세 설명·수치표 |
| 프로젝트 정책 | 주력 피해유형, 기본 체크, 최대 스택 가정, 기록 전용 분류 | 이 문서·v2·사용자의 명시적 판단 |
| 현재 구현 | 필드가 실제로 어떻게 계산·표시되는가 | 타입·로더·엔진·테스트 |
| 확인 필요 | 원문/데이터 불일치, 근거 부족, 표현 불가능한 효과 | 차이를 기록하고 판단을 보류 |

기존 데이터는 사례이지 모든 값이 정답이라는 근거가 아니다. 위키의 운영 팁이나 평가 문장도 스킬 상세 설명과 구분한다. 예를 들어 레베카의 공명 체인 2는 상세 설명에서 전체 속성 피해 보너스와 전체 피해 부스트를 구분하지만, 같은 페이지의 해설에서는 표현이 섞인다. 상세 설명을 우선 확인한다. [레베카 대조 자료](<https://namu.moe/w/레베카(명조: 워더링 웨이브)>)

원문과 구현이 충돌하면 원문을 바꾸어 해석하거나 엔진을 자동 수정하지 않는다. 현재 데이터, 원문 요약, 제안, 영향 범위를 나란히 제시한다. 사용자가 지정한 버전·수동 보정이 있으면 이를 보존하고 충돌을 알린다.

## 2. 변환 전에 준비할 입력

- 대상: 캐릭터/무기/세트 이름과 기존 ID. 기존 항목 수정인지 신규 추가인지.
- 원문: 스킬 상세 설명, 연결점 보너스, 공명 체인, 필요한 수치표. 요약 설명만으로 누락 여부를 판단하지 않는다.
- 출처: 원본 URL, 실제 열람 URL, 문서 제목·절 이름, 확인일, 확인 가능한 문서 개정 시각 또는 리비전.
- 기준: 게임 버전, 레벨, 스킬 레벨, 무기 공진 단계. 출시 전 자료라면 그 상태도 기록한다.
- 기존 데이터와 수동 결정: 유지할 값, 의도적으로 제외한 효과, 보정 이유.
- 관련 타입: [data.ts](../src/types/data.ts), [domain.ts](../src/types/domain.ts), 관련 데이터 항목, v2.

수집 과정에서 접기/펼치기, 표의 열 제목, `%`·`pt`, 스택 상한, 교대 시 종료 조건을 보존한다. 페이지 메뉴·스토리·음성·이미지 스타일 등 변환에 불필요한 내용은 제외한다. 원문 전체를 규칙 문서에 복제하지 않고, 근거 표에는 짧은 요약과 해당 절을 남긴다.

LLM이 URL을 실제로 열지 못했다면 열람했다고 표시하지 않는다. 검색 발췌만 확인한 경우와 본문을 확인한 경우도 구분한다. 미러는 원본과 동기화 시점이 다를 수 있으므로 원본 최신판 검증으로 간주하지 않는다.

## 3. 작성 절차와 출력 계약

1. 원문의 효과를 하나씩 추출한다. 하나의 문장에 공격력 증가와 별도 피해 배율 상승이 있으면 두 효과로 나눈다.
2. 각 효과에 `계산 반영 / 기록 전용 / 현 스키마 미지원 / 이번 작업 범위 밖 / 확인 필요` 중 상태와 이유를 붙인다. 데이터에 넣지 않는 효과도 추출 표에서는 누락하지 않는다.
3. 기존 항목과 대응시켜 `유지 / 추가 / 수정 제안`을 정한다. ID, 수동 보정, 기본 체크를 임의로 덮어쓰지 않는다.
4. v2에 따라 타입·대상·값·조건을 정하고, 합산·단위 변환 산식을 적는다.
5. 변환 초안과 근거 표를 함께 출력한다. 확인이 필요한 효과는 확정 데이터에 추측으로 넣지 않는다.
6. 사용자의 검수 범위와 승인에 따라 반영하고 검증한다. 사용자가 이미 수정 범위를 승인했다면 같은 허가를 반복해서 요구하지 않는다.

기본 출력 순서:

| 출력 | 포함할 내용 |
|---|---|
| 입력 요약 | 대상, 기준 버전·레벨, 출처·열람 상태, 기존 수동 결정 |
| 변환 초안 | 현재 저장 형식에 맞는 객체/배열 또는 변경 diff |
| 근거 표 | 필드/버프 ID, 원문 절·요약, 변환 값·산식, 조건·대상, 정책, 변경 여부 |
| 확인 필요 | 누락된 근거, 원문과 기존 값의 차이, 미지원 계산, 결정할 질문 |
| 검증 결과 | 실행한 검사와 결과, 아직 확인하지 못한 범위 |

근거 표 예시(원문을 요약한 것으로 직접 인용이 아님):

| 필드/ID | 원문 절·요약 | 변환 | 정책/변경 |
|---|---|---|---|
| `aemeath_star_wave_2` | 에이메스 고유 스킬·체인 3: 기본은 캐릭터별 스택, 체인 3은 조건 완화 | `critical_damage: 0.20`, `mode: wave`, `min_ascension: 0` | `default_on_from_ascension: 3`. 3돌 미만에도 파티로 가능하므로 잠그지 않음. 기존 유지 |

이 예시의 근거와 원문 접근 범위는 [v2 대조 기록](buff-recording-rules-v2.md#10-원문-대조-기록)에 있다.

## 4. 캐릭터 필드 작성 기준

전체 필수/선택 필드는 `Character` 타입을 따른다. 아래는 기계적 복사로 결정할 수 없는 부분이다.

| 필드 | 작성 기준 |
|---|---|
| `id`, `name` | 이름과 내부 ID를 구분. 신규 ID는 기존처럼 소문자·밑줄을 사용하되 중복 확인. 표기 교정만으로 기존 ID를 변경하지 않음 |
| `version`, `version_phase` | 게임 버전과 전반/후반을 확인. 현재 `version`은 숫자이므로 `3.10` 같은 표기는 `3.1`과 구분되지 않음. 그런 버전은 별도 스키마 판단 필요 |
| `element`, `weapon_type` | 게임 속성과 무기 종류를 `domain.ts`의 허용 값으로 대응 |
| `base_attack`, `base_hp`, `base_defense` | 장비·연결점 보너스가 합산되지 않은 기초 스탯. 레벨을 확인하고 출처에 남김. 모르는 값에 임의의 0을 넣지 않음 |
| `scale_stat` | 분석하려는 피해가 공격력/체력/방어력 중 무엇을 참조하는지 확인. 회복량 스케일만 보고 딜 스케일을 결정하지 않음. 체력/방어력 스케일이면 해당 기초값도 필요 |
| `damage_bonus_type` | 주력 공격이 실제 적용받는 피해유형. 버튼 이름과 구분. 변주 등 대응 유형이 없으면 기존 사례처럼 `null`을 쓸 수 있으나 이유 필요 |
| `effective_substats` | 해당 근사 계산에 유효하고 실제 에코 부옵으로 존재하는 스탯. 위키 인기 옵션을 그대로 복사하지 않음. `echo_skill_bonus`는 현재 부옵 단계표에 없음 |
| `modes` | 분석 결과·유효 옵션·버프 조건이 달라지는 모드를 표현. 모든 전투 자세를 자동으로 UI 모드로 만들지 않음 |
| `damage_type_mix` | 검토된 사이클별 피해 비중이 있을 때만. 출처·세팅·잔여분을 기록. 현재 갈브레나는 `0.571 + 0.321 = 0.892`; 나머지를 임의로 재분배하지 않음 |
| `skill_damage_coefficient` | 대표 피해의 배율을 소수로 저장하는 근사값. 어떤 스킬·레벨을 택했는지 필요. 모든 스킬 배율의 합이나 DPS를 의미하지 않음 |
| `energy_regen_mode` | `premise`: 필요 공명 효율을 전제로 분석. `deal_conversion`: 공명 효율을 자기 피해로 전환. `buff_conversion`: 공명 효율로 버프량이 변함. 엔진 지원 여부도 확인 |
| `default_required_energy_regen` | 공명 효율 목표치(예: 125). 공명 에너지 소모량 125pt를 그대로 복사하지 않음. 전환 상한 또는 별도 세팅 판단의 근거 필요 |
| `special_mechanism` | [등록된 키](../src/engine/mechanisms.ts) 또는 `null`. 현재 유일한 키는 `sigrika_er_to_echo`. 미지원 메커니즘 이름을 임의 생성하지 않음 |
| `recommended_*`, `signature_weapon` | 기존 무기/세트/메인 에코 ID를 참조. 추천은 원문 사실과 구분한 편집 판단. 전용 무기 없음과 정보 부족을 혼동하지 않음 |
| `cost_layout`, `matrix_cost` | 계산·편성 기본 정책. 현재 전원 `matrix_cost: 1`이라고 신규 게임 사실로 추정하지 않음. 코스트 문자열은 4/3/1, 1~5개, 합계 12 이하 검증 |
| `release_at`, `unreleased`, `notice` | 확인한 출시 상태만 반영. 날짜는 타임존 포함. `notice`는 안내이고 접근 잠금 기능은 아님 |
| `skill_node` | 연결점뿐 아니라 고유 스킬·회로·해방·반주·체인의 버프를 모은 배열. 일반 공격의 모든 배율표를 넣는 장소는 아님 |

## 5. 단위표

| 입력 의미 | 저장 예 | 주의 |
|---|---|---|
| 버프/무기 부가 스탯 12% | `0.12` | `value`, 백분율 `base_stats`, `refinement_values` |
| 크리티컬 피해 증가 500% | `5.0` | 기본 크리티컬 피해 `1.5`를 추가하지 않음 |
| 공명 효율 목표 250% | `250` | `default_required_energy_regen` |
| 동적 변환 기준 100% | `base: 100`, `threshold: 100` | 입력 기준은 퍼센트 숫자, 결과 `cap`은 소수 |
| 공명 효율 1%당 버프 0.25% | `per_percent: 0.0025` | v2의 계산 예시 참조 |
| 공격력 기초값 462 | `462` | 고정 스탯은 실제 숫자 |
| 조화도 파괴 증폭 40pt | `value: 40`, `type: harmony` | 기존 기록용 관례. 비율 효과와 같은 타입을 쓰므로 단위를 `note`에 명시 |
| 피해 비중 57.1% | `share: 0.571` | 근거 없는 비중 생성 금지 |

공명/협주 에너지 즉시 회복 `pt`를 `energy_regen`으로 바꾸지 않는다. 체력 회복량을 `hp_percent`나 `healing_bonus`로 바꾸지 않는다. 공격력의 N%만큼 입히는 피해는 공격력 증가 버프가 아니다.

## 6. 무기·세트·에코

- 무기 `base_stats.attack`은 기초 공격력, 나머지는 부가 스탯이다. 무기 패시브 공격력 증가는 `buffs`에 따로 기록하여 이중 합산을 피한다.
- 공진별 값은 1~5 순서로 5개를 기록한다. 등차수열이라고 추정해 빈 단계를 채우지 않는다. 최대 스택을 쓰면 다섯 값 모두 같은 스택 기준으로 환산한다.
- 세트의 2세트 효과와 5세트 효과는 별도 버프로 저장한다. `set_pieces`에 1/2/3/5를 명시한다. 5세트 행에 이미 기록한 2세트 값을 다시 더하지 않는다.
- 메인 에코 장착 패시브와 에코 발동 버프를 구분한다. 에코의 공격 배율 자체를 피해 보너스로 바꾸지 않는다. 코스트 3인 메인 에코는 `cost: 3`; 현재 생략 기본값은 4다.
- `two-piece-effects.json`은 실제 세트 목록이 아니라 자유 2세트 조합용 효과 풀이다. 전체 위키 세트를 여기에 추가하지 않는다.
- 착용자 원소 조건과 수혜자 원소 조건은 별개다. `provider_element`와 `element`의 차이는 v2를 따른다.

## 7. 사람이 수정한 데이터 재생성

- 원문 변화와 수동 정책 변화를 구분한 diff를 만든다. 전체 파일을 재정렬하거나 다른 캐릭터를 함께 정리하지 않는다.
- 기존 ID는 저장된 선택·토글의 식별자다. 새 번역이나 문구 정리에 맞춰 변경하지 않는다.
- 원문이 없어졌다는 이유만으로 기존 버프를 삭제하지 않는다. 개정·수집 누락·버전 차이를 확인한다.
- 사람이 정한 `default_on`, 추천, 필요 공명 효율, 피해 비중은 근거가 달라졌을 때만 수정 제안한다.
- 신규 관례(예: 조건부 버프 ID 명시)를 기존 전체 데이터에 자동 소급하지 않는다.
- 기존 데이터에 없는 효과를 찾으면 미기록인지 의도적 제외인지 표시한다. 모르는 의미를 `value: 0`으로 채워 유효 데이터처럼 제출하지 않는다.

## 8. 검수와 검증

문서 검수에서는 출처 절, 실제 데이터 ID·수치, 코드 경로, 원문 사실과 근사 정책의 구분을 확인한다. 이번 문서의 대조 범위와 불일치는 v2 §10~11에 기록되어 있다.

향후 데이터 수정 시에는 다음을 확인한다.

- 타입/로드: 필수 필드, 허용 문자열, 두 점수 플래그, 스킬 노드의 `target`·`min_ascension`.
- 참조: ID 중복, 추천/전용 무기 존재·무기 종류, 세트·메인 에코 관계, 모드 참조, 대상 캐릭터 존재. 현재의 `rover` 같은 미등록 참조는 예외로 보고한다.
- 값: 단위, 최대 스택, 공진 5개 값, 돌파 추가분, 동적 값의 기준선·상한. 스킬명/피해유형과 효과 대상의 누락.
- 계산: 새 타입 또는 기존과 다른 동적 타입 조합은 실제 집계 경로를 확인. 타입 검사를 통과했다고 계산 지원을 단정하지 않는다.
- 표시: 관련 캐릭터의 모드·돌파·공진을 바꾸어 토글과 수치 확인. 파티 제공 효과는 제공자/수혜자 양쪽에서 확인.

프로젝트의 현재 검증 명령:

```sh
npm run build
npm test
```

`build`는 TypeScript 검사와 Vite 빌드를 실행한다. JSON 로더의 검증은 테스트에서 확인한다. 이 명령들이 원문과 데이터의 의미 일치를 증명하지는 않는다. 계산을 바꾸는 효과를 추가할 때는 해당 효과를 분리해 확인하는 테스트가 필요하다. 문서만 수정할 때는 링크·예시·변경 범위 검증으로 충분하다.

## 9. LLM에 전달할 지시문

아래 지시문과 이 문서, v2, 관련 타입, 기존 대상 데이터, 원문을 함께 전달한다. 파일 접근이 없는 LLM에는 실제 내용을 첨부한다.

```text
제공한 위키 자료를 wuwa-scouter 데이터 초안으로 변환한다.
data-authoring.md와 buff-recording-rules-v2.md를 따른다.
원문 사실, 프로젝트 근사 정책, 현재 구현, 확인 필요 항목을 구분한다.
계산 대상은 에코에서 얻을 수 있는 효과와 같은 종류의 스탯 버프다.
특정 스킬 배율 증가·배율 가산·추가타는 기록 전용으로 두고 계산에 포함하지 않는다.
특정 스킬의 크리티컬 피해 등 일반 스탯 증가와 스킬 배율 자체의 변경을 구분한다.
기존 ID와 수동 수정은 보존하고 변경 제안에는 근거를 붙인다.
효과별 수혜자, 발동 조건, 피해유형, 단위, 스택, 돌파, 공진을 확인한다.
한 문장에 여러 효과가 있으면 분리하고 제외한 효과에도 이유를 남긴다.
불명확하거나 미지원인 효과는 추측하여 확정 데이터에 넣지 않는다.
입력 요약 → 변환 초안 → 근거 표 → 확인 필요 → 검증 결과 순서로 출력한다.
현재 저장 형식은 JSON이다. TS 전환은 별도 요청이 있을 때만 한다.
실제로 확인하지 못한 출처나 실행하지 않은 검사를 완료했다고 쓰지 않는다.
```
