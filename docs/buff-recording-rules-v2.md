# 버프 기록 규칙 v2

2026-09-14 작성. [작성 절차](data-authoring.md)와 함께 사용하는 개정안이다. [기존 문서](buff-recording-rules.md)는 유지한다. 최초 대조 이후 사용자 요청에 따라 확인된 데이터·엔진 오류를 수정했으며, §11에 결과와 남은 한계를 기록했다. 이 문서는 기존 관례를 설명하되, 원문과 맞지 않는 관례를 자동으로 정답으로 만들지 않는다.

근거 표기: **원문 확인**은 위키에서 확인한 효과, **프로젝트 정책**은 근사 계산을 위한 선택, **구현 확인**은 현재 코드 동작, **확인 필요**는 충돌·미지원·출처 부족이다. 원문 확인은 게임 내 실측 검증을 뜻하지 않는다. 대조 출처와 열람 한계는 §10을 참조한다.

## 1. 효과를 읽는 순서

1. **무엇이 바뀌는가:** 스탯, 피해 보너스, 피해 부스트, 기존 보너스의 배수, 스킬 배율, 추가타, 이상효과, 자원/스택.
2. **누가 받는가:** 본인, 파티, 다음 등장 캐릭터, 본인 제외 파티, 특정 캐릭터.
3. **어느 피해에 적용되는가:** 속성, 실제 피해유형, 특정 스킬, 이상효과.
4. **언제 가능한가:** 모드, 공명 체인, 스택, 발동 조건, 지속·종료 조건.
5. **값을 어떻게 얻는가:** 고정값, 최대 스택, 기존 효과의 추가분, 공진별 수치, 제공자 스탯에 따른 동적 값.
6. **현재 모델이 표현하는가:** 계산 반영/기록 전용/미지원/확인 필요를 결정.

단어 하나로 타입을 결정하지 않는다. 특히 영어 `increased DMG`를 무조건 `_amplify`로 매핑하지 않는다. 공격력 증가·피해 증가·기존 보너스 수치 상승은 연산 대상이 서로 다르다.

## 2. 타입과 계산 반영 정책

**사용자 확정 기준:** 계산에는 에코에서 얻을 수 있는 효과와 동일한 종류의 스탯 버프를 반영한다. 특정 스킬의 데미지 배율 자체를 올리는 돌파·버프는 반드시 기록만 하고 계산에서 제외한다. 출처가 돌파인지 고유 스킬인지보다 **무엇을 증가시키는 효과인지**가 기준이다.

| 효과 | 판정 |
|---|---|
| 공격력·크리티컬·속성/유형 피해 보너스 등 에코와 같은 스탯 증가 | 계산 대상 |
| 특정 스킬의 배율 가산·상대 증가·추가타 | 기록 전용, 계산 제외 |
| 특정 스킬에 붙는 크리티컬 피해 등 에코와 같은 스탯 증가 | 계산 대상. 특정 스킬 배율 증가와 구분 |

허용 키의 원본은 [domain.ts](../src/types/domain.ts)다. 이 목록은 버프·주옵·부옵이 공유하므로 **키가 존재한다는 것과 버프로 계산된다는 것은 다르다.**

| 의미 | 타입 | 신규 작성 기준 |
|---|---|---|
| 크리티컬 확률/피해 증가 | `critical_rate`, `critical_damage` | 증가분만 소수로 저장 |
| 공격력/체력/방어력 비율 증가 | `attack_percent`, `hp_percent`, `defense_percent` | 실제 스탯 증가인지 확인 |
| 고정 스탯 | `flat_attack`, `flat_hp`, `flat_defense` | 현재 일반 버프 집계는 미지원. 부옵 경로와 혼동 금지 |
| 공명 효율 증가 | `energy_regen` | 자원 즉시 회복 pt와 구분 |
| 치료 효과 증가 | `healing_bonus` | 기록 가능하나 현재 딜 계산에는 미반영 |
| 속성 피해 보너스 | `element_damage_bonus` | 원소 지정 시 `element`; 전체 속성이면 `전체` 사용 가능 |
| 유형 피해 보너스 | `basic_attack_bonus`, `heavy_attack_bonus`, `resonance_skill_bonus`, `resonance_liberation_bonus`, `echo_skill_bonus` | 실제 피해유형에 대응 |
| 속성/전체/유형 피해 부스트 | `element_damage_amplify`, `all_damage_amplify`, 각 유형의 `*_amplify` | 원문 효과와 적용 범위를 확인 |
| 기존 유형 보너스 합계에 곱하는 효과 | `damage_type_bonus_factor` | 일반적인 최종 피해 부스트와 구분 |
| 특정 스킬 배율·한정 피해 강화 | `skill_motion_value_bonus`, `skill_motion_value_amplify` | 반드시 `record_only: true`, `absolute_score_only: false`. 계산 제외 |
| 이상효과 피해 강화/추가타 | `anomaly_damage_amplify`, `anomaly_damage_additional` | 일반 딜과 별도. 추가타의 `value`는 배율 |
| 조화도 관련 수치 | `harmony` | 기록 전용. pt/비율/스택 의미를 `note`에 명시 |
| 방어력/속성 저항 무시 | `defense_ignore`, `element_resistance_ignore` | 원문이 저항 감소인지 무시인지도 보존. 동일시 가능 여부 검토 |

### 피해유형과 스킬명

**원문 확인:** 시그리카 공명 해방은 에코 어빌리티 피해로 판정된다. **프로젝트 정책:** 주력 판정에 따라 캐릭터의 `damage_bonus_type`을 `echo_skill`로 둔다. 해방 버튼을 쓴다는 이유로 `resonance_liberation_bonus`를 유효 옵션에 넣지 않는다. [시그리카·공명 해방](https://namu.moe/w/시그리카)

한 캐릭터의 모든 공격이 같은 유형이라는 뜻은 아니다. 여러 피해유형을 합치는 경우 `damage_type_mix`의 비중 근거가 별도로 필요하다.

### 증가·부스트·취약·기존 보너스 배수

- 속성/유형 **피해 보너스 증가**는 해당 `_bonus`로 기록한다.
- **피해 부스트**는 적용 범위의 `_amplify`로 기록한다.
- **받는 피해 증가**는 기존 모델에서 취약을 `_amplify` 버킷으로 근사한다. 일반 유형 전체인지 특정 스킬 한정인지도 확인한다. 게임의 모든 취약 효과가 다른 부스트와 같은 버킷이라고 단정하지 않는다.
- **전체 피해 보너스 증가**는 `element_damage_bonus`와 `element: 전체`로 합산한다. 린네 공명 해방의 24%가 사례다. 기존 보너스 100%라면 `(1 + 1.00 + 0.24) / (1 + 1.00) = 1.12`이며, 최종 피해에 1.24를 곱하지 않는다. [린네 스킬·분석](https://www.prydwen.gg/wuthering-waves/characters/lynae)
- **기존 보너스가 N% 상승**하면 그 보너스가 연산 대상이다. 레베카 6돌의 현재 구현은 유형 보너스 합 ×1.4이다. `basic_attack_bonus: 0.4` 또는 최종 피해 ×1.4로 대체하지 않는다. [레베카·공명 체인 6](<https://namu.moe/w/레베카(명조: 워더링 웨이브)>)

### 특정 스킬 한정 효과

프로젝트는 대표 피해로 에코 옵션 효율을 근사한다. 다음 분류는 사용자가 확정한 계산 범위이며, 게임의 보편 공식에 관한 주장이 아니다.

- 특정 스킬에만 붙는 크리티컬 피해 등 일반 스탯 증가도 대표 피해의 버프로 반영하는 사례가 있다. 히유키 독심/납도 크리티컬 피해 +500%는 `critical_damage: 5.0`, 두 플래그 `false`이며 기본 체크는 꺼져 있다. 적용 범위와 대표 피해 가정을 문구·근거 표에 남긴다. [히유키·공명 체인 6](https://namu.moe/w/히유키)
- 특정 스킬의 배율·한정 피해 강화는 반드시 `record_only: true`로 제외한다. 에이메스 종결 +25%, 레베카·갈브레나의 돌파 배율 증가, 구원의 배율 가산이 사례다. `skill_motion_value_*`에 `record_only: false`를 넣으면 로더가 오류로 거부한다. 스킬 이름이 있다는 이유만으로 일반 스탯 증가까지 이 분류에 넣지는 않는다.
- 이상효과에 새로 부여되는 고정 크리티컬 확률/피해는 일반 크리티컬 증가분으로 계산하지 않는다. 기존 에이메스 6돌처럼 기록 전용으로 두고, 고정값임을 명시한다.
- 추가타, 배율의 퍼센트포인트 가산, 기존 배율의 상대 증가는 서로 다르다. 기록 전용 키가 같더라도 `note`와 근거 표에 원래 연산을 남긴다. 서로 다른 두 효과를 하나의 `value`로 뭉개지 않는다.

## 3. 두 플래그의 의미와 한계

| `record_only` | `absolute_score_only` | 현재 의미 |
|---|---|---|
| false | false | 일반 반영 대상으로 기록. 실제 반영은 타입·대상·조건·집계 지원에 따름 |
| false | true | 부스트·방어력/저항 무시 등의 분류 표식. 계산 포함 대상 |
| true | false | 일반 버프 계산과 일반 버프 패널에서 제외 |
| true | true | 금지. 로더가 오류 처리 |

**구현 확인:** [buffs.ts](../src/engine/buffs.ts)는 `record_only`로 제외하지만 `absolute_score_only`로 계산을 분기하지 않는다. `absolute_score_only: true`만 붙인다고 상대 점수에서 제거되는 것이 아니다. 비교하는 두 빌드에 **동일한 상수 배수로 적용될 때** 비율에서 약분된다. 공명 효율 등에 따라 배수도 변하면 무조건 약분된다고 할 수 없다.

`anomaly_damage_amplify`, `anomaly_damage_additional`, `harmony`는 [일반 버프 패널](../src/components/BuffPanel.tsx)의 숨김 타입이며 현재 일반 딜 집계에도 계산 분기가 없다. 그래서 두 플래그가 false여도 딜에 포함되지 않는다. 이상효과 스택 상한만 기록한 기존 항목처럼 `record_only: true`인 사례도 있어, 이상효과의 플래그를 일괄 통일하지 않는다.

치료 효과도 두 플래그만으로 딜 반영 여부를 설명할 수 없다. “두 플래그가 false면 반드시 점수 반영”이라는 규칙은 사용하지 않는다.

## 4. 필수 필드와 조건

| 적용 범위 | 요구 사항 |
|---|---|
| 저장하는 모든 `Buff` | `type`, `value`, `always`, `record_only`, `absolute_score_only` 명시 |
| 캐릭터 `skill_node` | `target`, `min_ascension` 명시. 체인 조건 없음은 `0` |
| 신규 조건부 버프 | 안정적인 `id`, 조건이 드러나는 `label`·`short`, 기본 체크 기준 명시 |
| 공진별 변화 | `refinement_values` 5개. `value`는 동일 조건에서 1공진 값 |
| 세트 효과 | `set_pieces` 명시. 메인 에코 자체 패시브에는 붙이지 않음 |
| 동적 값 | `energy_scale` 또는 `crit_scale`과 기준·상한·수혜자 확인 |

타입에서 선택 필드인 것과 작성 시 필수인 것은 다를 수 있다. 엔진이 만드는 임시 버프에는 저장 데이터의 필수 규칙을 그대로 적용하지 않는다.

- `always`는 상시 효과인지 나타낸다. 쉽게 유지된다는 이유만으로 조건부 효과를 상시로 바꾸지 않는다. 상시여도 모드·원소·돌파 조건은 먼저 검사된다.
- `min_ascension`은 이 프로젝트에서 공명 체인 0~6의 잠금 조건이다. 캐릭터 레벨 돌파나 스킬 레벨을 넣지 않는다.
- `default_on`은 UI/근사 세팅의 기본 선택이다. 실제 발동 감지나 가동률이 아니다. 일반적인 유지 가능 상태를 기본으로 삼되 파티·특정 스킬에 의존하면 근거를 남긴다.
- `default_on_from_ascension`은 특정 체인부터 기본 체크한다. 그 아래에서 수동 활성화할 수 있다. 신규 작성 시 `default_on`과 동시에 넣지 않는다.
- 현재 조건부인데 ID가 없는 버프가 18개 있다. 이를 신규 작성의 표준으로 삼지 않는다. 기존 ID를 추가·변경하면 파티 토글의 인덱스 기반 식별자도 달라질 수 있으므로 별도 변경으로 다룬다.
- 지속시간·쿨타임·교대 종료·중첩 불가 조건은 전용 필드가 없다. `label`/`note`와 근거 표에 남긴다. 그 문구만으로 엔진이 시간·발동 조건을 자동 검증하지는 않는다.

## 5. 대상과 적용 조건

| `target` | 의미 | 본인 계산 / 파티 제공 |
|---|---|---|
| `self` | 소유자 본인 | 본인만 |
| `party` | 본인 포함 파티 | 본인 및 파티 제공 |
| `next_character` | 다음 등장 캐릭터 | 본인 제외, 파티 기능에서 제공 |
| `party_except_self` | 본인 제외 파티 | 본인 제외, 파티 기능에서 제공 |
| `specific_character` | `target_character` ID의 캐릭터 | 해당 ID만 수혜 |

반주라는 출처만 보고 `next_character`로 고정하지 않는다. 양양·현령 반주는 본인 제외 파티에 적용되므로 현재 `party_except_self`가 사용된다. 히유키 반주도 같은 대상 표현에 맞춰 `party_except_self`로 수정했다. [양양·현령·반주](https://m.namu.moe/w/양양·현령)

적에게 붙는 효과도 게임상 디버프 위치가 아니라 **누구의 피해에 적용되는지**로 `target`을 정한다. 특정 캐릭터의 피해만 늘어나는 취약을 파티 전체 버프로 확장하지 않는다.

- `element`: 피해를 받는 적의 원소가 아니라 적용받는 캐릭터/피해의 속성 필터. `전체`는 현재 수혜자 원소 필터를 통과한다.
- `provider_element`: 착용자/제공자의 원소 조건. 파티 공격력을 올리는 응결 전용 착용 효과를 `element: 응결`로 쓰면 수혜자까지 잘못 제한할 수 있다.
- `only_character`: 착용자 제한. `target_character`는 수혜자 제한이다.
- `mode`: 해당 소유자의 분석 모드와 일치할 때 활성. 다른 모드 효과를 합쳐 저장하지 않는다.
- `damage_bonus_type`, `exclude_damage_bonus_type`: 현재는 분석 캐릭터의 주력 유형을 비교하는 필터다. 실제 개별 타격을 판별하는 기능이 아니다. 파티 제공 목록에서는 제공자의 모드/주력 유형으로 검사하고, 전달 시 이 필드를 보존하지 않는다. 제공자 발동 조건과 수혜자 피해 범위를 혼동하지 않는다.
- `target_damage_bonus_type`: 수혜자의 주력 피해유형 필터. 파티 전달 후에도 보존한다. 루실라 줌은 `echo_skill`로 제한한다. 개별 타격이나 혼합 피해의 크리티컬을 분리하는 필드는 아니다.

**구현 한계:** 현재 파티 기능은 교대 순서와 시간 경과를 시뮬레이션하지 않는다. `next_character`가 실제 다음 순서에만 전달됨을 보장하지 않는다. 원문 대상은 정확히 기록하되 이 한계를 잘못된 대상 선택으로 숨기지 않는다.

## 6. 스택·추가분·공진

### 고정 최대 스택

한 효과의 발동 조건과 스택 상한이 같으면 `스택당 값 × 채택 스택 수`를 한 버프로 기록한다. 추가 최대 스택 보너스가 있으면 그것도 계산하되, 다른 종류의 효과는 분리한다. 기본 체크가 켜졌다고 모든 파티에서 최대치가 보장되는 것은 아니다.

**원문 대조:** 시그리카 축복은 파티 보너스 3%×6과 최대 스택에서 본인 추가 30%를 구분한다. 현재 데이터도 원소/에코 피해 각각 `party: 0.18`, `self: 0.30`으로 나눈다. 본인 합 48%를 파티에 제공하면 안 된다. [시그리카·함의의 공명](https://namu.moe/w/시그리카)

루시 백도어의 전체 피해는 `0.10 × 2 + 0.05 = 0.25`다. 원문에 함께 있는 해킹 배율 상승은 별도 효과로 추출해야 한다. [루시·고유 스킬](<https://www.namu.moe/w/루시(명조: 워더링 웨이브)>)

### 파티·돌파별 스택

에이메스는 기본 조화 파동 모드에서 캐릭터별 20%씩 최대 3스택, 불꽃 모드에서 30%씩 최대 2스택이다. 체인 3에서 조건이 완화된다. 현재 데이터는 추가 스택을 별도 토글로 두고 `min_ascension: 0`, `default_on_from_ascension: 3`으로 표현한다. [에이메스·별과 별 사이/공명 체인 3](https://namu.moe/w/에이메스)

아래는 현재 `aemeath_star_wave_2` 데이터와 같은 구조의 예시다.

```json
{
  "type": "critical_damage",
  "value": 0.20,
  "always": false,
  "target": "self",
  "mode": "wave",
  "id": "aemeath_star_wave_2",
  "min_ascension": 0,
  "label": "별과 별 사이(조화 파동) 2스택 · 크피 +20% (3돌 자력 또는 파티원)",
  "short": "크피 +20% (파동 2스택)",
  "record_only": false,
  "absolute_score_only": false,
  "default_on_from_ascension": 3
}
```

기존 예시의 약어 문구는 원형을 보존했다. 신규 `label`은 §9의 풀네임 규칙을 따른다. 스택 토글 사이의 선행 스택 의존성까지 엔진이 강제하는 것은 아니다.

### 기존 효과 강화는 추가분만

기본 버프가 계속 활성인 상태에서 체인 보너스를 추가한다면 **추가분**을 저장한다. 갈브레나의 기본 공격력 보너스 20%를 350% 강화하는 현재 표현은 기본 `0.20`과 추가 `0.20 × 3.5 = 0.70`이다. 합계 `0.90`을 추가 버프로 또 넣지 않는다. [갈브레나·공명 체인 2](https://namu.moe/w/갈브레나)

아우구스타도 체인별 왕관 스택 증가분을 따로 저장한다. 교체 효과라면 기본값과 동시에 적용되는지부터 확인한다. 상한 증가만 있는 효과를 새로운 완성 버프 하나로 복사하지 않는다.

### 공진과 스택을 함께 처리

가을의 무늬는 공진별 스택당 공격력 4/6.2/8.4/10.6/12.8%에 최대 5스택을 적용하여 아래 배열을 사용한다. [치사·추천 무기/가을의 무늬](<https://namu.moe/w/치사(명조: 워더링 웨이브)>)

```json
{
  "value": 0.20,
  "refinement_values": [0.20, 0.31, 0.42, 0.53, 0.64]
}
```

위 블록은 전체 `Buff`가 아닌 수치 필드 예시다. 엔진은 공진별 값을 `value`에 **대체**하므로 두 값을 더하지 않는다.

## 7. 동적 버프

동적 데이터에는 고정 최대치만 저장하지 않는다. 현재 `value`는 0인 사례와 상한값인 사례가 혼재한다. 지원되는 동적 계산 경로에서는 계산값으로 대체하며, 중복 가산하지 않는다. 신규 동적 버프는 `value: 0`과 계산 파라미터를 쓰되, 전달 경로까지 지원되는지 확인한다.

### 공명 효율 → 버프

현재 [energyScaleValue](../src/engine/mechanisms.ts)의 정의:

```text
ER = 공명 효율의 퍼센트 숫자 (260%이면 260)
value = min(per_percent × max(0, ER - base), cap)
base 생략 시 100
```

| 사례 | 파라미터 | 검산 |
|---|---|---|
| 모니에 간섭 표기 | `per_percent: 0.0025`, `base: 100`, `cap: 0.40` | 260%에서 `0.0025 × 160 = 0.40` |
| 파수인 심층 크리티컬 | `per_percent: 0.0005`, `base: 0`, `cap: 0.125` | 250%에서 `0.125` |
| 파수인 해금 크리티컬 피해 | `per_percent: 0.001`, `base: 0`, `cap: 0.25` | 250%에서 `0.25` |

모니에는 초과분, 파수인은 총량을 사용한다. 파수인 원문의 0.2%당 0.01%는 `0.0001 / 0.2 = 0.0005`로 환산한다. [모니에·간섭 표기](https://namu.moe/w/모니에), [파수인·결말의 순환](https://namu.moe/w/파수인)

**구현 확인:** 자기 버프 집계에서 `energy_scale` 결과를 받는 타입은 `critical_rate`, `critical_damage`, `attack_percent`, `element_damage_bonus`, `all_damage_amplify`다. 깃털 세트의 공격력 전환과 수수의 전체 피해 보너스 전환도 자기 계산에 반영한다. 파티 전달은 제공자의 저장 빌드 공명 효율로 값을 먼저 계산한다. 다른 타입 조합을 추가할 때도 집계 지원을 확인한다.

수수 산안개의 `per_percent`는 `0.001 / 0.12`를 충분한 정밀도의 JSON 숫자 `0.008333333333333333`으로 저장한다. ER 200/230/260%에서 각각 공격력 0/25/50%가 된다.

### 크리티컬 확률 → 크리티컬 피해

```text
CR = 상한 적용 전 크리티컬 확률의 퍼센트 숫자
value = min(per_percent × floor(max(0, CR - threshold)), cap)
```

구원은 `threshold: 50`, `per_percent: 0.02`, `cap: 0.30`; 아우구스타는 체인 2에서 기준 100/상한 1.0, 체인 6 추가분에서 기준 150/상한 0.5다. **정수 퍼센트로 내림하는 것은 현재 코드의 규칙**이며, 원문의 “1%당”만으로 게임도 반드시 내림한다고 단정하지 않는다. [구원·진중한 한 수](<https://namu.moe/w/구원(명조: 워더링 웨이브)>), [아우구스타·공명 체인](<https://namu.moe/w/아우구스타(명조: 워더링 웨이브)>)

**구현 확인:** [파티 전달 코드](../src/state/store.ts)는 `energy_scale`과 `crit_scale` 모두 제공자의 저장 스탯으로 계산하며 표시값과 수혜값을 공유한다. 구원 크리티컬 50/60/65%에서 파티 크리티컬 피해는 0/20/30%다. 제공자 빌드가 미저장·미완성이면 UI에 빌드 저장 필요·미적용을 표시하고 계산값은 0이며 상한을 임의 적용하지 않는다. 제공자의 파티 편성은 재귀 계산하지 않는 기존 한계가 있다.

### 시그리카의 별도 전환

`special_mechanism: sigrika_er_to_echo`는 `min(0.50, max(0, ER - 125) × 0.02)`를 자기 피해유형 보너스에 더한다. 125% 이하 0, 150% 이상 0.50이다. 같은 효과를 `skill_node`에 고정 50%로 다시 추가하지 않는다. 기존 레지스트리를 재사용하며 신규 키는 엔진 변경 없이 생성하지 않는다.

## 8. 계산 모델의 경계

- [perf.ts](../src/engine/perf.ts)는 증가 보너스 합과 부스트 합을 각각 `1 + 합계`로 곱하는 근사식이다. 모든 개별 부스트를 각각 독립 곱으로 계산하는 모델은 아니다.
- `record_only`는 미해결 항목을 아무 타입에나 넣어도 된다는 뜻이 아니다. 자료에는 남기되 적절한 필드가 없으면 미지원 목록으로 분리한다.
- 캐릭터의 한정 크리티컬 버프는 현재 단일 크리티컬 기대값에 들어간다. 특정 타격만 받는 효과를 정확히 분배하는 것은 아니다.
- `damage_type_mix`는 입력한 비중을 사용한다. 갈브레나 비중은 현재 데이터값으로 확인했으며, 이번 위키 대조로 그 정확한 수치의 출처를 확인하지 못했다.
- 이상효과 추가타·해킹·조화도·지속시간·교대·자원 회복은 일반 딜에 완전하게 모델링되어 있지 않다. 미반영을 효과 자체가 없다는 뜻으로 설명하지 않는다.

## 9. 문구와 식별자

- `label`: 출처/발동 조건 → 수혜자 → 효과·값 → 지속시간/체인. 신규 문구는 크리티컬 확률·크리티컬 피해·방어력 무시처럼 풀어 쓴다.
- `short`: UI용 요약. 크리·크피·방무 같은 기존 약어는 허용하되 중요한 대상/조건을 제거하지 않는다.
- 부스트는 “부스트”, 피해 보너스는 “피해 보너스/증가”로 구분한다. 해석이 미확정인데 문구부터 부스트로 단정하지 않는다.
- `{v}`는 공진에 따라 바뀌는 수치 표시용이다. 동적 값은 기준·상한을 설명하고 현재값 표시는 엔진 경로를 확인한다.
- `note`: 스택당 수치와 최대 스택, 추가분 산식, 원문 단위, 한정 범위, 근사 선택 이유.
- 하나의 버프 ID에는 한 효과만 대응시킨다. 신규 ID는 실제로 같이 선택될 수 있는 버프들과 충돌하지 않게 정한다. 기존 `guwon_*`, `*_intro_*` 등의 철자만 보고 출처나 인물을 재해석하거나 이름을 고치지 않는다.

## 12. v1에서 달라진 기준

- 단어 치환보다 효과의 연산 대상·범위·원문 절을 먼저 확인한다.
- 기록 대상과 계산 지원을 구분하고, 미기록·미지원 효과도 검수 표에 남긴다.
- `target` 다섯 종류, 제공자/수혜자 원소, 모드·피해유형 필터를 설명한다.
- `absolute_score_only`를 강제 계산 분기나 무조건 약분되는 약속으로 설명하지 않는다.
- 최대 스택 외에 파티 조건, 체인 추가분, 기존 보너스 배수, 공진별 스택을 구분한다.
- 동적 수치의 단위·산식·내림과 파티 전달 한계를 명시한다.
- 실제 대조 출처와 미확인 범위를 기록하고, 기존 예외를 신규 규칙으로 자동 승격하지 않는다.
